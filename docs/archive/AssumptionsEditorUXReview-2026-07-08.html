Impact List · Interface Review

The Assumptions Editor, Reconsidered

The machinery under /assumptions is honest and well-guarded. The friction that remains lives in four places — the words, the drill-in loop, the feedback, and the shell — each traced through the source, with a menu of fixes.

Date  July 8, 2026 Scope  /assumptions — library panel, differences view, three tabs, effect editors, save/share flows Method  Static review of source (~30 files); mockups are code-derived, app not run

TL;DR

The bones are strong. The page's best architectural idea — user assumptions stored as a minimal diff against defaults — is visible to the user: a "differences from default assumptions" disclosure itemizes every customization with before → after values, provenance notes, and one-click reverts. Un-applied edits are guarded against navigation loss. Computed values render as readouts, not fake inputs, with the whole card as the edit affordance. The three tabs are real folder tabs, and tab/entity state lives in the URL with working back/forward. None of the options below touch that machinery.

What remains clusters in two places. The words: the page speaks two vocabularies at once — an overloaded word ("unsaved" means both un-applied and not-saved-to-browser) and machine identifiers promoted to user-facing labels ("Effect 1: population", "Cost per microprobability"). The drill-in loop: effect editors replace the list they came from (comparing two causes means close, reopen, repeat) and run a preview year of their own. The single highest-leverage move is human display names for effects (option 1.1) — raw ids currently sit on two primary surfaces, and every other copy fix reads better once names are human.

§ 1

The machine as built

Naming the parts precisely first, because one of the findings is that the page names itself three times. A visitor meets three stacked headings for one surface — "Assumptions" AssumptionsPage.jsx:321, "Current Assumptions" SavedAssumptionsPanel.jsx:26, and "Edit/View Assumptions: …" AssumptionsEditor.jsx:414 — above a library dropdown, a differences disclosure, three folder tabs, and drill-in editors.

Worth keeping, explicitly: the differences disclosure and its diff engine — before → after rows that resolve inherited recipient values to concrete numbers with "from cause" and "× n" provenance notes, per-row revert included utils/assumptionsDiff.js, ReviewChangesSection.jsx; the navigation guard covering both global and drill-in drafts (tab switches and the browser back button included) plus its beforeunload backstop AssumptionsEditor.jsx:186; value-gated draft preservation (the Global form rehydrates per-parameter by value, and drill-in editors re-initialize only when their own baseline changes — so unrelated reverts and loads never clobber in-progress typing) useGlobalForm.js, useRecipientEffectsDraft.js; honest readout cards with per-entity accessible names AssumptionEntityCard.jsx; URL-backed tab/entity state useAssumptionsEditorController.js; the indigo "customized" color language; validation that blocks bad commits loudly; scroll position preserved across editor open/close shared/ScrollToTop.jsx. None of the options below sacrifice these.

§ 2

Four root causes of friction

Eleven individual issues are catalogued in §3; they are symptoms of four underlying causes. Fix causes, not symptoms.

Root cause 1 · HighOne page, two vocabularies

The page's remaining confusion is mostly lexical, in two species:

  • "Unsaved" means two things. The verbs themselves are now location-named — "Apply" commits a draft to the active set AssumptionsEditor.jsx:433, "Save to browser" keeps a named copy — but the state word behind them is still overloaded: the navigation guard speaks of un-applied drafts, while the dropdown's "Custom (unsaved)" constants/customAssumptionsEntry.js:5 means not saved to this browser — so a user who just clicked Apply is immediately told their work is unsaved anyway. And a three-paragraph tooltip on "Current Assumptions" SavedAssumptionsPanel.jsx:27 still does the work a sentence of visible copy should.
  • Machine identifiers in user space. Effect cards are titled "Effect 1: population" EffectCard.jsx:35 — content-frontmatter ids promoted to primary labels — and the differences rows chip the same raw ids ReviewChangesSection.jsx:23, so ids now sit on two primary surfaces. Field labels like "Cost per microprobability" constants/effectFieldDefinitions.js:24 each carry a paragraph of tooltip, and the editor's header help exits to the FAQ mid-task CategoryEffectEditor.jsx:208.
  • Labels that hedge or overspecify. "Edit/View Assumptions" hedges. "Fixed" pills on two Global cards never say why those parameters are fixed GlobalValuesSection.jsx:82. The default library entry bakes a parameter value into its name — "Default (100 years)" constants/assumptionsLibraryEntries.js:5 — doing disambiguation work that belongs in a description. And "Default" (Global tab) vs "Baseline" (drill-ins effects/QalyEffectInputs.jsx:18) encode a real distinction — a recipient's baseline is inherited from the cause including your cause edits — that is never explained where it appears, so precision reads as inconsistency.

Root cause 2 · MediumThe drill-in hides the list it came from

Opening a cause or recipient editor replaces the whole tab panel AssumptionsEditor.jsx:473. Leaving mid-edit is handled well — the tabs stay live, and a dirty draft gets the same Apply-and-leave / Discard / Keep-editing prompt that protects global edits — but the list context is still gone: comparing two causes means close → reopen → repeat, and the figures you were scanning vanish the moment you start editing one of them. A slide-over editor (option 2.1) keeps the world visible behind the edit session.

Root cause 3 · MediumFeedback gaps in the editing loop

  • Two preview years that don't sync. The list header has a year selector AssumptionsEditor.jsx:59; each drill-in initializes its own CategoryEffectEditor.jsx:38 — so the number you drilled in from can differ from the number the editor shows, with no cue why.
  • Applying is silent. Library actions notify ("loaded", "saved"); Apply — the moment the entire site recalculates — says nothing. The highest-consequence event on the page is its quietest.
  • Recipient search caps at 10 results with no count and no way to see more useAssumptionsForm.js:24.

Root cause 4 · MediumA shell that narrates itself three times

Three stacked headings introduce one surface (Fig. 1, A–C), and the third — "Edit/View Assumptions: X" — repeats the label shown directly above it in the panel that also owns the dropdown and the differences view. The panel footer hosts a site-wide display preference AssumptionsPage.jsx:358 that has nothing to do with the library. The shell spends its space saying what things are called instead of letting the one real hierarchy (library → state → editor) show.

§ 4

Options — Tier 1: words & copy (S–M; no architecture changes)

1.1

Humanize effect names at the source

Add displayName (and optionally a one-line summary) to effect frontmatter in content/categories/*.md, thread it through the generator and validation, and render "Existential catastrophe from AI" instead of "Effect 1: population" — on effect-card titles, differences rows, and editor headers alike. Keep the raw id as small print for cross-referencing with the written justifications.

Why
The single highest-leverage remaining move. Raw ids sit on two primary surfaces (effect cards and the differences view), and every other copy fix in this tier reads better once names are human.
Effort
M — touches content schema, generator, validation, and three render sites; mechanical throughout.
1.2

One meaning per word — a rename pass

A coordinated pass over labels so each verb maps to exactly one layer of Fig. 2, and each reference word to one concept:

  • "Custom (unsaved)" → "Edited — not saved to this browser" (its description already says this; the label should).
  • Notify on Apply: one sentence through the existing notification context — "Assumptions applied — rankings site-wide now use them." Fixes the feedback asymmetry and teaches Apply's scope in the moment it matters.
  • "Baseline" → keep, but let it explain itself once per surface: "Baseline (from cause): $X". "Default" stays for Global.
  • "Fixed" → the pill's tooltip gains the actual reason those two parameters can't be edited.
  • "Default (100 years)" → "Impact List defaults", with the time-limit note in its description, so a future default change doesn't falsify the name.
Effort
S — copy plus one notification call.
1.3

One preview year

Lift the drill-in editors' year state up to the list's existing previewYear so the year you previewed in the list is the year the editor shows, with one consistent label ("Cost to save a life in 2026").

Effort
S.
1.4

Trim the shell

Retire the "Edit/View Assumptions: X" heading — the panel directly above already names the active set, offers its actions, and itemizes its differences; the tab strip is self-explanatory without a title. Move the "show selector on every page" preference out of the library panel footer into a low-key settings row at the bottom of the page. Shrink the three-paragraph tooltip to one line by promoting its load-bearing sentence ("these assumptions drive every calculation on the site") into visible microcopy under the panel heading.

Why
One heading, one switcher, one status surface — the layout stops repeating itself and the hierarchy (library → state → editor) becomes the visible structure.
Effort
S–M — layout surgery in AssumptionsPage.jsx / SavedAssumptionsPanel.jsx / AssumptionsEditor.jsx, no logic changes.
§ 4

Options — Tier 2: the editing loop (M each; change how editing feels)

2.1

Slide-over editors

Open cause/recipient editors in a right-side sheet (a wide ModalShell variant — the focus/Escape/scrim machinery already exists) over the dimmed list, instead of replacing the panel. URL semantics stay identical; Apply/Cancel become the sheet's footer; closing returns to a list that never went away.

Why
Resolves RC2 at the root: the list survives the edit session, so compare-and-edit stops requiring round trips. The navigation guard already handles dirty exits — the sheet is pure presentation on top of machinery that exists.
Cost
The multi-category editor is long — the sheet needs comfortable width (~min(720px, 90vw)), internal scroll, and a full-screen fallback on small viewports.
Effort
M.
2.2

Auto-apply Global — a product decision, now de-risked

Remove the Apply layer on the Global tab: valid values commit on blur/debounce; invalid ones hold with the existing field errors. Drill-ins keep Apply/Cancel — they're modal sessions, which is a coherent split. The engineering preconditions are already in place: the differences disclosure narrates what changed with per-row reverts (the safety net), and the form's per-parameter value-aware rehydration means live commits can't clobber typing elsewhere.

Why
Deletes the Draft layer for the tab most users touch first — and with it the "unsaved" double meaning (issue #2) and the global half of the navigation guard's job, rather than renaming around them.
Cost
Mid-typing recalculation (mitigated by blur-commit; the calculations are memoized and cheap); users lose "stage several parameters, apply once" batching. Genuinely a product call about how the page should feel, not an engineering question.
Effort
M.
§ 4

Options — Tier 3: bigger bets (L; rethink pieces of the model)

3.1

Worldview-first landing

Reframe the page's opening move from "here are three tabs of parameters" to "here are worldviews — pick, compare, then customize." Curated profiles become cards with one-line philosophies and headline consequences ("longtermist: AI risk dominates; global health ~$8K/life"); editing is the second act. The current editor remains, one level in.

Why
Most visitors will never edit a microprobability; they want to know whether the rankings survive their worldview. This serves that majority and makes the editor an advanced mode rather than the front door.
Cost
A real product decision about the page's purpose, not just its layout; adds a level of hierarchy power users must click through (mitigate: deep-link straight to the editor).
3.2

Plain-language effect editing

Present each effect as a sentence with editable slots, generated from the same fields — the raw grid stays behind "Show raw fields" for power users. The FAQ's explanations move into the control itself.

Why
The current fields describe the math's variables; the sentence describes the belief. Beliefs are what users came to edit. Kills the paragraph-tooltip pattern (RC1) at its root, and composes naturally with 1.1's display names.
Cost
Sentence templates per effect type (two exist today) and careful input widths; validation messages need sentence-aware placement. The highest-craft item here, and the one that would most distinguish the site.
3.3

Comparison mode

"Compare" any two assumption sets: side-by-side parameter diff plus consequence deltas — top-10 donor rank shifts, biggest cause cost movements. Turns the library from storage into an instrument, and gives shared links a reason to circulate ("look how our rankings differ"). Notably cheaper than it sounds: the diff engine and its row renderer already exist utils/assumptionsDiff.js, ReviewChangesSection.jsx — the new work is the rank-delta computation and a view.

Cost
L — a dedicated surface; purely additive to everything above.
3.4

Sliders coupled to the future-value graph

Global parameters get bounded sliders (with exact-entry fields kept) wired live to GlobalFutureValueGraph, so discount rate and time limit are felt — the curve moves under your thumb. Pairs naturally with 2.2.

Cost
M — choosing honest bounds is the hard part; the graph exists.
§ 5

What I'd do, in order

  1. 1.1 first — effect display names. It's the prerequisite: effect cards, differences rows, and any future editor phrasing all read better the moment names are human, and every step below inherits it.
  2. 1.2 + 1.4 together — the rename pass and the shell trim are one sitting of copy-scale diffs. Afterward each verb means one thing, Apply announces itself, and the page introduces itself once instead of three times.
  3. 1.3 — one preview year. Small, isolated, closes issue #4.
  4. 2.1 — slide-over editors, the one structural item left. The guard already made leaving an edit safe; this makes staying in context possible, and closes issue #3.
  5. Then decide 2.2 (auto-apply Global) as the product call it is — the engineering risk is already retired. Treat Tier 3 as separate bets: 3.2 first if the goal is editing quality, 3.1 if the goal is reach.

What I would deliberately not do: add more tooltips — the fix for words under the page is words on the page; allow typing into the computed cause/recipient readouts (back-solving a cost per life into effect parameters is underdetermined and would falsify the effects model); build a second "what have I changed" surface (tab badges, counts elsewhere) — the differences disclosure is the single home for that answer, and duplicating it re-creates the ambiguity it resolved; or mix apply models across tabs beyond the deliberate 2.2 split.
