# src/components/assumptions/ — the assumptions editor

The editing UI for global parameters, category effects, and per-recipient effect overrides. Rendered inside `AssumptionsEditor.jsx` (component root one level up) on the `/assumptions` page, with tab/entity selection held in the URL.

## Structure

- `GlobalValuesSection` / `CategoryValuesSection` / `RecipientValuesSection` — the three tabs' list/summary views.
- `AssumptionEntityCard` — the cause/recipient list card. The cost per life is a computed READOUT (not an input — it's derived from effect parameters); the whole card is a widened pointer target that opens the editor, with the inner Edit button as the keyboard/AT path (same pattern as AssumptionsDropdown rows). Entity link and action buttons stop propagation.
- `ReviewChangesSection` — collapsible "Differences from default assumptions" disclosure rendered by `AssumptionsPage` inside the Current Assumptions panel (state metadata lives with the state controls, not the editing surface): the userAssumptions-vs-defaults diff (`utils/assumptionsDiff.js`) with per-row revert via `setAllUserAssumptions`. Renders nothing at zero changes and stays available while a drill-in editor is open — safe because the effect editors' draft re-initialization is VALUE-gated (`getBaselineReinitSignature`, which unlike `getEffectsSignature` sees `_baseEffect`), so reverting an unrelated row leaves in-progress drafts alone while reverting the edited entity's own row — or its cause's — re-initializes them against the restored baseline.
- `AssumptionsEditor` (one level up) also owns the unapplied-edits navigation guard (`useBlocker` + `beforeunload` + `UnappliedEditsModal`), covering BOTH kinds of draft: un-applied Global form edits block only pathname changes (the form survives same-page tab switches), while a dirty drill-in draft blocks any navigation that would close or retarget its editor — tab switches, entity switches, and the browser back button included — compared via `getEffectEditingTargetFromSearch`. Tabs are never disabled; the guard replaces the old lock. The three drill-in editors report dirtiness through `onUnsavedChangesChange` (`hooks/useUnsavedChangesReporter`) and expose `attemptApply()` on a forwarded ref (see the EFFECT_EDITOR_HANDLE_CONTRACT comment in AssumptionsEditor) so "Apply and leave" can commit the payload directly and let the blocked navigation supply the exit; the editors' own Apply/Cancel exits clear the dirty flag ref-first because they navigate in the same tick. When BOTH draft kinds are dirty, "Apply and leave" is deliberately non-atomic: the drill-in payload commits first, and a global validation failure then cancels only the navigation (see the handleApplyAndLeave comment; pinned by the "holds invalid global edits" page test). `useBlocker` requires the app's data router — tests must render through `createMemoryRouter` (see the page test helpers).
- `CategoryEffectEditor` — edits a category's effects (direct field values); owns the category-flavor draft logic.
- `RecipientEffectEditor` / `MultiCategoryRecipientEditor` — edit a recipient's per-category effect **overrides/multipliers** (not direct values). Multi-category recipients get one section per category. Both are thin shells around `hooks/useRecipientEffectsDraft` (the entire draft state machine — unit-tested; change edit behavior THERE) and `RecipientEffectCard`.
- `EffectCard` — the card chrome shared by all three editors (title/toggle/cost row, active-interval note, disabled dimming); `RecipientEffectCard` composes it with the recipient override inputs. Optional `rationaleHref` renders a "Why these values?" link (cause editors target the cause page's `#full-justification`, recipient editors the recipient page's). Known wording trade-off, accepted deliberately: the justification explains the PUBLISHED values, so mid-edit the label slightly overpromises — the unedited case dominates and the form marks defaults inline. Per-effect anchors are a follow-up: content headings aren't consistent enough for text-derived slugs (only ai_capabilities uses "Effect N:" headings).
- `effects/` — per-type input layouts: `QalyEffectInputs`, `PopulationEffectInputs`, and recipient variants that adapt overrides onto the same layouts via `useRecipientEffectAdapter`. Field ids are `effect-{index}-{field}` plus an optional `fieldIdPrefix` — the multi-category editor passes `{categoryId}-` because each of its sections indexes effects from 0, and duplicate DOM ids would break label and aria-errormessage associations (pinned by the page suite's unique-id test).
- `TabNavigation` — textbook ARIA tablist; copy its pattern for new tabbed UI. Optional per-tab `badges` render an amber count whose text is exposed as the tab's accessible DESCRIPTION (`aria-describedby` to a hidden span), so the tab's accessible NAME stays its label — role/name queries and announcements don't change when a badge appears.
- **Global draft-status layer** (in `AssumptionsEditor`): a Global draft survives tab switches but its Apply button doesn't, so the draft stays visible on its own — an `.assumptions-draft-chip` count beside Apply plus a bulk **Discard** (resets to applied values, available even while validation errors block Apply), a count badge on the Global tab, a "Global has N unapplied changes — Review" toolbar reminder whenever the Global Apply isn't rendered (other tabs, open drill-ins), and draft-preview labeling on the future-value graph. The graph labels itself a preview by comparing RESOLVED preview parameters against applied ones — not form dirtiness — because invalid draft fields resolve back to their applied values. Vocabulary/color contract: draft indicators say "unapplied" and use the amber warning hue; the blue edited/custom hue and the word "differences" belong to APPLIED state (the panel's differences view), and the two layers never mix.
- **Preview year**: the editor shell owns ONE `previewYear`, shared by the list views AND all three drill-in editors (passed down with its setter) — a list set to 2010 can never silently disagree with an editor's costs. All computation uses `resolveCalcYear(previewYear)` (a defensive guard — see below), and computed labels name that same resolved year ("Combined cost per life in 2010:", per-effect "Cost per life in 2010:"). `YearSelector` is semi-controlled: partial/out-of-range text stays local to the control and only valid in-range years are committed to the parent, so consumers never see `''` or absurd transient years mid-typing; blur clamps out-of-range input to the bounds and restores the committed year when left empty — never a silent jump to the current year. It takes `ariaLabel` for callers that embed it mid-sentence with `label=""`. The multi-category editor's per-section cost reports are tagged with their calculation year, and the header aggregates only reports matching the current year — a year change can't paint the new year's label over the old year's aggregate.

## The data model the editors speak

- Category effect edits are stored as direct fields: `{effectId, costPerQALY: 123, disabled?}` — only diffs from defaults survive `normalizeUserAssumptions`.
- Recipient effect edits are wrappers: `{effectId, overrides: {field: value}, multipliers: {field: factor}, disabled?}`. An override and multiplier for the same field are mutually exclusive (setting one clears the other).
- Draft state in the editors is stringly (users type partial values like `"-"` or `"1,0"`); `effectEditorUtils.cleanEffectsForSave` converts to numbers at save and throws on garbage. Preview costs use `calculateEffectCostPerLife`, which renders expected mid-typing states as Infinity ("N/A").
- Editor drafts carry an internal `_baseEffect` reference for display purposes — it must NEVER reach `normalizeUserAssumptions`/saved state (validation would reject it as an unknown field). The save paths strip down to the wrapper shape.

## Testing

Recipient draft logic is unit-tested in `src/hooks/useRecipientEffectsDraft.test.js` (init, stringly overrides, override/multiplier exclusivity, validation errors, disable toggling, the save shape — which carries recipient default overrides forward because user override sets replace them wholesale at combine time — and baseline reinitialization). Editor UI behavior is covered by the `AssumptionsPage.test.jsx` integration suite and the e2e smoke specs — run both after changes here.
